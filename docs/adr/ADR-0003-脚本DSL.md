## 背景

架构文档 §4.3 指出，默认允许任意 Python 脚本会带来：

- 无法静态分析脚本会做什么；
- 无法准确列出能力；
- 难以回放和确定性测试；
- 可以绕过策略层直接操作系统；
- 分享脚本等于分享可执行代码，供应链风险很高；
- 同一脚本在不同机器上的依赖不可控。

任务文档 §1.1 不变量 5 进一步冻结：普通脚本使用声明式 YAML/JSON；M0-M3 禁止任意 Python、Shell、DLL 或系统命令执行。

## 决策

1. **从第一版就使用 YAML/JSON 状态机**：声明式脚本编译为状态机运行；Python 只用于实现平台内置检测器与适配器，不作为脚本执行载体。
2. **M0-M3 禁止任意 Python、Shell、DLL 或系统命令执行**：DSL、导入包和 UI 均无 `exec`/`eval`/shell 入口（SEC-001）；插件机制默认关闭。
3. **两层模型**：
   - **普通脚本**：纯声明式 YAML/JSON，只能使用注册动作和检测器；
   - **开发插件**：单独安装、显式授权、能力声明、独立进程；后期可考虑 WASM 插件，而不是在主进程中 `exec()` Python（M4，PLG-001/002）。
4. **静态检查为发布前提**（架构文档 §5.1，由 DOM-007 在 M2 实现）：
   - 所有状态都能到达；
   - 所有非终态都有超时或退出条件；
   - 不允许无限循环且无预算；
   - 所有动作都能映射到已声明能力；
   - 真实输入只能出现在允许的目标配置；
   - 在线目标配置不能启用无人值守调度；
   - 模板、ROI、标定引用必须存在且有哈希；
   - 迁移条件必须引用已定义的感知字段；
   - 脚本 schema 必须可迁移、可锁版本。

## 理由

- 声明式 DSL 换来静态检查、可视化编辑、确定性回放、版本迁移、能力约束、安全分享和自动测试（架构文档 §14 决策 3）；
- 能力默认拒绝（DOM-005）配合静态分析，使"脚本不能绕过 Policy Guard"成为编译期与运行期双重结论；
- M0-M3 完全关闭任意代码入口，使一票否决项"任意脚本/导入包可执行 Python、Shell、DLL、系统命令或绕过 Input Broker"在结构上不可能发生，而非仅靠测试发现。

## 后果与影响

- 前期 Schema 设计工作量增加（DOM-001~004），为发布冻结与迁移（ADR-0007）奠定基础；
- DSL 演进受 Schema 版本迁移纪律约束（DOM-004、GOV-005）；
- 插件机制推迟到 M4，且必须满足独立进程、显式能力、可撤销权限、版本锁和哈希、无管理员权限、崩溃不影响输入代理释放按键（架构文档 §6.2 第 12 项）；
- 条件表达式语法必须白名单化（FSM-001：只允许白名单运算和感知字段，禁止任意代码、反射和系统调用）。
