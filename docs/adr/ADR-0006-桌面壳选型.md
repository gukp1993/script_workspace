## 背景

技术主线为 Vue3 + TypeScript 前端 + Python 本地服务（架构文档 §0）。需要一个桌面壳把 Vue 页面嵌入原生窗口，并桥接 Python 后端。候选方案为 pywebview 与 Tauri。

## 决策

- **MVP（M1）使用 pywebview 承载 Vue3 工作台**：Vue 页面嵌入原生窗口、Python-JS 桥接、快速打包，最符合当前 Vue3 + Python 技术栈；
- **产品化阶段（M4 起）评估 Tauri 壳**：当需要签名、自动更新、系统 WebView、托盘、通知和更强桌面能力时启动评估，Python 运行时作为 sidecar；
- 换壳不改变 ADR-0001 的进程职责与 ADR-0002 的 IPC 安全边界：桌面壳始终不直接发送输入，崩溃时不得留下按键按下状态，异常退出触发 Broker 清理（UI-001）。

## 理由

- pywebview 允许复用既有 Vue3 与 Python 技能栈，M1 即可交付桌面壳、目标选择与预览，避免壳工程过早消耗排期；
- Tauri 涉及 Rust 工具链、签名证书与 sidecar 进程治理，应在产品化需求（更新、签名、托盘）明确后再引入；
- 壳只是承载层，安全边界全部位于控制面、运行时与 Input Broker，换壳不会削弱不变量。

## 后果与影响

- UI-001 交付 pywebview 桌面壳与启动流程，桌面壳启动/关闭能正确管理后端子进程；
- M1 不承诺自动更新、托盘与签名发布；相关能力归入 M3（REL-003 签名）与 M4（通知、托盘、更新、Tauri 评估）；
- 若引入 Tauri，须新增 ADR 说明 IPC 变更（见 ADR-0002 产品化路线）；
- 壳的 Python-JS 桥接同样受 Origin/令牌约束（ADR-0002），不得提供绕过控制面的直连通道。
