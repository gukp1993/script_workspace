## 1. 使用约定

- 每个任务先满足 DoR，再进入开发；**P0 安全任务不可被功能任务跳过**。
- 任务完成必须同时满足 DoD 全部条目；存在例外时必须在评审记录中写明豁免原因与负责人。
- 与本文配套的 PR 评审清单见 `docs/governance/review-template.md`。

## 2. Definition of Ready（DoR）——任务进入开发前必须具备

来源：任务文档 §2.3。全部勾选方可开工：

- [ ] **目标**：任务要解决什么问题、与哪个任务 ID / 需求 ID 对应（需求追踪见 TST-011）；
- [ ] **范围外内容**：明确本任务不做什么，防止范围蔓延；
- [ ] **依赖**：上游任务 ID（含 GOV/ENG/DOM 等前置项）已满足或已约定并行接口；
- [ ] **输入样例**：可供开发与测试使用的数据、帧、轨迹或 Schema 样例；
- [ ] **接口或 UI 草图**：跨模块契约、消息格式或界面示意已给出；
- [ ] **可验证验收标准**：能写成断言或测试用例的完成标准（不是"做完"而是"怎么算对"）；
- [ ] **测试责任人**：谁负责验收测试与回归；
- [ ] **数据准备说明**：测试数据、夹具、黄金数据集的准备方式与归属。

## 3. Definition of Done（DoD）——任务完成必须同时满足

来源：任务文档 §2.4。全部勾选方可关闭任务：

- [ ] **代码合并**：变更已合并入目标分支（主分支不允许带静态检查错误合并，ENG-004）；
- [ ] **类型检查和 Lint 通过**：Python/TypeScript 静态检查全绿；
- [ ] **单元/组件测试**：新增或修改逻辑有对应测试，必要时契约测试同步更新；
- [ ] **错误与取消路径**：错误分支、取消、超时与安全停止路径已实现并有测试；
- [ ] **结构化日志**：关键事件有结构化日志与 `correlation_id`（ENG-005）；
- [ ] **必要文档**：接口说明、使用说明或 ADR 已更新（若架构决策变化，先补 ADR）；
- [ ] **无未声明能力**：未引入能力清单之外的能力，未绕过 Policy Guard / Input Broker；
- [ ] **相关回放/黄金数据更新**：影响视觉/状态机/输入的变更已附回放差异并更新黄金基线；
- [ ] **QA 可独立复现**：验收步骤、数据与环境说明足以让 QA 独立复现结果；
- [ ] **无 P0/P1 遗留缺陷**：本任务引入的缺陷已修复或按缺陷分级规则获得豁免（任务文档 §14）。

## 4. 开发节奏补充约定（任务文档 §2.2）

- PR 必须通过静态检查、单测、契约测试；**影响视觉/状态机/输入的变更必须附回放差异**。
- 每周至少一次跨模块演示，以 ArenaLab 场景为准，**不以真实在线游戏作为开发调试环境**。
- 每个里程碑都生成候选版、测试报告、未关闭缺陷和风险豁免清单。
